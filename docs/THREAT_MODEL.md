# Threat Model

This draft covers one Unraid instance with a public short-link domain, a private admin domain, a reverse proxy, a local SQLite volume, and optional network integrations. It uses OWASP Top 10:2025 to frame the risks and defines defensive checks for release. [OWASP Top 10:2025](https://top10.owasp.org/2025/) · [OWASP Cheat Sheet Series](https://cheatsheetseries.owasp.org/)

## Assets, Actors, and Trust Boundaries

| Boundary | Data and trust assumptions |
| --- | --- |
| Internet → proxy → public listener | Treat incoming host, URL, user agent, and header values as untrusted. Accept validated forwarding information only from the configured immediate peer. The public listener returns the defined destination and may consume an authorized access. |
| Browser or API client → admin listener | Clients may be authenticated, compromised, or underprivileged. Check permission for the requested action and object. Network restrictions reduce reachability. The application also authenticates requests. |
| Processes → data volume | The volume contains destination URLs, history, configuration, password and token digests, analytics, and integration credentials. Docker and host administrators and privileged backup operators have broad access. File and backup permissions are part of the operating model. |
| Import file or restore archive → parser → staging → live data | Treat files, data, and schema metadata as untrusted even when an administrator selects them. Read import inputs without modifying them. Change live state only after validation and approval. |
| Admin-authored public pages → sanitizer → public listener | Treat template files and pasted HTML as untrusted even when an administrator imports them. Only a browser session can change pages. Custom HTML is sanitized on save and on load, served without scripts under a hash-based CSP, and password and one-time forms stay server-generated. The preview is framed only by the admin origin in a sandbox. |
| QR logo PNG → authenticated upload → QR renderer | Treat logo bytes as untrusted. Limit the body, dimensions, concurrent reads, decode allocations and work. Generate SVG from sampled pixels. Discard the input after rendering. |
| Scheduler and fetcher → network | Title retrieval, preview images, monitoring, webhooks, and connectors can reach sensitive internal systems if their policies are wrong. Treat DNS as input and bind credentials to a single approved connector. A preview image URL comes from the destination page, so a malicious page chooses where the next request goes: it gets the full public address policy, the destination policy, and its own size and time limits. |
| Destination image → decoder → admin interface | Treat preview image bytes as hostile, including the declared type. Accept only PNG, JPEG, WebP, GIF, or a PNG inside an ICO, chosen by magic bytes, never SVG. Bound the download (2 MiB), dimensions (4,096 per side), and decoded allocation (64 MiB), decode on a blocking thread with pure-Rust decoders, and store only a re-encoded JPEG thumbnail without metadata. Serve it from the admin origin with `nosniff`, a fixed type, and the admin CSP. |
| Admin session → operations settings → outgoing requests | Turning on health checks, title lookup, and preview images, the scheduled backup interval and retention, and the notification webhook, its Authorization header, and its events were container-only and can now be changed through an admin session. A stolen session can therefore start outgoing requests or redirect notifications. The webhook and header require a fresh password confirmation, are write-only, and pass the same address validation as container values. The connector origin and networks, hosts, proxies, rate limits, and listeners stay environment-only. |
| Build and release → operator | Git, CI runners, artifacts, the registry, base images, and dependencies can affect the binary and all data it can access. Keep image provenance and build versions traceable. |

Relevant actors and inputs include visitors and bots, requests arriving through a misconfigured proxy, compromised browsers or API keys, malicious or compromised destination servers, tampered import files, and a compromised build ecosystem. Failures can result from power loss, process termination, an incorrect restore artifact, a full disk, or long-running WAL readers. Anyone with unauthorized read access to the data volume can copy the database contents visible to them. A fully compromised host or major upstream network outage is outside the application's control.

## Threats and Release Criteria

P0 identifies release blockers or risks of near-total compromise. P1 identifies risks with severe impact on data, accounts, or public URLs. P2 identifies more limited risks that still require review before release. The following checks are planned acceptance criteria.

| ID | Threat and impact | Priority | Planned controls | Acceptance criteria |
| --- | --- | --- | --- | --- |
| T01 | Admin takeover during setup, session fixation, or credential attacks | P0 | Local single-use token, transactional setup, bounded Argon2id concurrency, rotation and revocation, rate limits | Concurrent setup attempts create exactly one administrator. Verify that completion and recovery revoke the applicable prior sessions and setup tokens. |
| T02 | Public or underprivileged admin actions, access to another object's ID, or scope bypass | P0 | Separate route tables, authorization per action and object, deny by default, scope and domain filters on reads and writes, typed request and response data, closed CORS policy. Implemented: single-link reads and per-link analytics summaries resolve the link inside the key's host and return 404 otherwise, and link reads omit traffic fields without the analytics scope | Maintain a route inventory and test unauthorized reachability and permissions for GET, mutations, bulk operations, exports, and jobs, including guessed IDs. |
| T03 | Server-side access to internal data, DNS changes, unchecked redirects, or connector credential leaks | P0 | Central fetcher, narrowly scoped connector policies, validation of all addresses, connections pinned to validated addresses, revalidation at each hop, distinct credentials, system proxies disabled by default. Implemented: one pinned HTTPS notification connector with CIDR ranges, private CA roots, and a header credential sent only to the configured webhook without redirects. A webhook saved in Settings › Operations follows the same validation, cannot change the connector, and a literal non-public address is refused when entered. Preview image URLs taken from a destination page get the full public policy and the destination policy for each image request and every redirect hop, without the connector. | Use controlled test doubles to compare the validated address with the actual connection. Disallowed address classes or unauthorized destination changes stop the job before the outbound connection is opened. |
| T04 | Host or forwarding header manipulation, proxy abuse, or inconsistent path normalization | P1 | Trusted peer network allowlist, proxy overwrites forwarding headers, one parsing policy, configured domains, canonical admin origin, byte-for-byte redirect tests. Implemented: another admin address gets `404` with a static page that names no configured address, host, or version, and the API keeps its problem response | Direct and proxied requests apply the same host rules. Unknown hosts are rejected. Nginx Proxy Manager fixtures verify path resolution and the response of manually recreated URLs. |
| T05 | Access beyond the configured limit, preview consuming a one-time link, or caching that bypasses a limit | P0 | Database transaction before sending Location, expiring signed confirmation, exact origin, Argon2id password verification, and `no-store`. Implemented: password attempts count per client and process and also per client and link and per link across clients, so one guessed link cannot exhaust every other link's attempts | Verify concurrent confirmation and the absence of a destination in GET and HEAD responses. Confirm `303` prevents resending the password. Previously cached permanent redirects survive server policy changes. |
| T06 | Tampered destinations, header, SQL, log, or HTML injection, or XSS from imports or previews | P0/P1 | Validated HTTP(S) URLs, typed headers, parameterized queries, text rendering, raster asset decoding and sanitization, strict CSP, rejection of raw SVG uploads. Implemented: custom public pages pass an allowlist sanitizer that rebuilds the markup on save and on load, are served without `script-src`, with styles by hash, `img-src data:`, `form-action 'self'`, and `frame-ancestors 'none'`, and fall back to the built-in page when invalid | Invalid input produces a structured rejection or displays as text. Valid signed URLs and fragments remain intact. |
| T07 | Import or restore crossing file or database boundaries, or accidental modification of source data | P0 | Read-only inputs, format and schema version checks, staging, size and integrity checks, safe paths, supported data parsing, approved cutover | Partial, corrupt, unsupported-version, and oversized datasets stop in staging. Abort and recovery tests leave either the original or the new valid dataset. An older supported snapshot must carry an exact prefix of the embedded migration history and the schema those migrations produce before the embedded migrations upgrade a private staged copy. A failed upgrade leaves the live database and the source file unchanged. |
| T08 | Token or personal data exposure through logs, history, exports, backups, URL referrers, or external services | P1 | Log allowlist, secret redaction, minimal default fields, browser-only history with bounded retention and manual purge, protected downloads, synthetic CI data, opt-in integrations. The stored-backup list is browser-only and read-only, returns file names without paths, skips symbolic links, and offers no stored-file download. A saved webhook URL and Authorization header are never returned by the API and are removed from verified snapshots, together with the saved health check, title lookup, and preview image switches. Preview rows keep only the image URL's origin, not its path or query | Verify history access and restore scope. Ensure password and key material stays out of revision payloads. Treat historical destinations and backup snapshots as confidential. |
| T09 | Service degradation due to denial of service, SQLite FULL or BUSY, or resource or queue exhaustion | P1 | Distinct resource budgets, bounded traffic queues, readiness checks, timeouts, drop counters, fail-closed access limits, backoff, verified backups. Implemented for preview images: one worker, one link per pass, at most three image requests of 2 MiB each, decoder limits of 4,096 pixels per side and 64 MiB, a blocking decode thread, and 48 KiB per stored thumbnail | Run load and fault injection tests with controlled local resources. Read-only redirects continue when the data can be read safely. A limited access requires a committed write before the redirect. |
| T10 | Phishing through short links, imported public page templates, or rapid abuse of a leaked write key | P1 | Authenticated creation, scopes, immediate deactivation, an opt-in destination host policy enforced on writes and on every redirect, an informational unusual-traffic indicator, auditing, expiring and rotatable API keys. Implemented: public pages change only through a browser session with audit and security notification, imports show a sanitized preview of every page before they apply, and reset to the built-in page is always available | Revoking a key or disabling a link prevents new use without a restart. An enabled destination policy refuses writes and redirects to refused hosts without consuming visit allowances or one-time access. Explain known external cache limits for 301 and 308 in the interface. |
| T11 | Tampered releases, outdated dependencies, or compromised CI | P0/P1 | Tagged versions, locked builds, pinned actions and images, SBOM, advisory and license checks, image scans, minimal CI permissions, review | Attach the bill of materials, build digest, and scan results to the release. Block release while critical or high-severity risks remain open. |
| T13 | Abuse of an admin session to start outgoing requests or redirect notifications through operations settings | P1 | Browser-session-only routes with Origin and CSRF, API keys refused, password grant for the webhook and its header, write-only secrets, validation of the whole effective combination, audit entries by setting name with a `security` notification. Implemented in 0.9.0 | Tests verify that a webhook change without a fresh grant fails, the grant is used once, API keys get `401`, responses and the audit log never contain the URL path or header value, and refused changes save nothing. |
| T12 | Repeating jobs indefinitely, sending old notifications after restore, or replaying old sessions | P1 | Idempotency, send limits, deduplicated outbox, integration pause on restore, active session revocation, historical jobs marked complete. Implemented: deterministic event keys, eight capped attempts, stale expiry after 24 hours, and discarding pending notifications, title lookups, and preview fetches after a restore | Restart and restore tests verify that sending prior messages requires approval and that restored sessions are rejected. |

## Risk Assessment and Evidence

The highest risks are an unintentionally exposed admin listener, privileged outbound requests, undetected changes to recreated link paths or access limits, and irreversible restore failures. The defensive test matrix covers integrity, reachability, and interruption with local test data. Bot and Geo-IP classifications expose uncertainty and possible false positives. External caches, visitor behavior, and third-party software also affect the results. Open requirements and release gates are tracked in the decisions, security design, and test plan.
